# clap-tui refactor plan

Based on the current architecture review and the present crate layout.

This plan is an internal-architecture companion to
`agent-docs/2026-03-15-2052-clap-feature-implementation-plan.md`.
It is not intended to make the crate production ready on its own; it is
intended to make the feature work land on cleaner, more durable seams.

## Objective

Improve internal architecture without changing the public user experience:

1. reduce coupling between interaction logic and rendering/layout helpers
2. replace broad mutable state access with narrower seams
3. make new interaction features additive instead of switch-heavy
4. preserve current runtime and library ergonomics unless there is a clear gain
5. create better internal seams for the richer clap model and validation flow in the companion feature plan
6. establish one correctness pipeline from editable input state through argv construction and validation

## Principles

- no rewrite
- keep milestones independently shippable
- preserve current keyboard, mouse, preview, and argv behavior
- avoid hardening internal seams around the current simplified clap model when the companion feature plan is about to replace it
- establish and document public extension points early enough that later refactors do not optimize around the wrong library contract
- add tests before moving logic that is easy to regress

## Non-goals

- this plan alone does not close clap feature coverage gaps
- this plan alone does not make `clap-tui` production ready
- no broad event-loop rewrite

## Current problems to target

### 1. Reducers and navigation depend on view/layout code

`update` and `controller::navigation` currently call `view::form`, `view::command_tree`, `view::argv`, and `ui::dropdown::dropdown_layout`.

Impact:

- layout changes can affect behavior
- interaction logic is harder to test in isolation
- a second frontend or headless mode would be expensive

### 2. `AppState` is too open

Most internal modules can directly mutate `state.domain`, `state.ui`, and `state.notifications`.

Impact:

- invariants are spread across files
- future features will keep adding hidden coupling
- smaller internal abstractions are harder to introduce

### 3. Action handling is centralized and extension-hostile

New behavior requires edits across keyboard dispatch, mouse dispatch, `Action`, and `update::apply_action`.

Impact:

- weak OCP
- high merge pressure in a few files
- interaction growth will make the system harder to reason about

### 4. Public seams are reviewed too late

If runtime boundaries and supported extension points are only reviewed after the
internal cleanup, earlier phases may optimize around the wrong library contract.

Impact:

- internal cleanup may preserve abstractions that are not the right long-term seams
- public API review becomes reactive instead of shaping the refactor
- production-readiness decisions get deferred until the end

### 5. Semantic rules and widget/presentation rules are still mixed

`InputPresentation` is used by serialization and interaction logic even though it partly reflects widget choices.

Impact:

- semantic changes and widget changes are not cleanly separated
- serialization depends on presentation categories

### 6. Correctness logic does not yet have one authoritative pipeline

Preview argv, omission/default behavior, and validation are still at risk of
being split across serializer helpers, view helpers, reducers, and the final run
path.

Impact:

- correctness rules can leak across unrelated layers
- preview and run paths can drift apart
- richer clap semantics become harder to add without duplicating logic

## Refactor sequence

## Phase 0: Confirm public seams and coordination points

Goal: make the rest of the refactor serve the library contract rather than the
other way around.

### Work

- Confirm which extension points are intentionally supported during the refactor:
  - custom runtime
  - theming/configuration
  - command startup selection
- Record which changes are expected to remain internal even if their shape changes.
- Cross-reference the companion clap feature plan so architectural work does not
  entrench the current simplified spec or input model.
- Note any public API constraints that later phases must preserve unless there is
  a compelling simplification gain.

### Target files

- `crates/clap-tui/src/runtime.rs`
- `crates/clap-tui/src/lib.rs`
- `README.md`
- `agent-docs/2026-03-15-2052-clap-feature-implementation-plan.md`

### Acceptance criteria

- supported extension points are documented before the deeper refactor starts
- later phases have explicit public constraints to preserve or justify changing
- the refactor sequence is aligned with the companion feature plan

## Phase 1: Introduce application queries and commands

Goal: remove direct dependence on `view::*` from reducers and navigation.

### Work

- Add an internal query layer for behavior-oriented lookups:
  - visible args for the active tab
  - selected form item
  - visible command tree items
  - argv preview
- Move these queries out of `view` modules into a neutral internal module, for example `model` or `query`.
- Keep `view` code focused on rendering concerns only.

### Target files

- `crates/clap-tui/src/update.rs`
- `crates/clap-tui/src/controller/navigation.rs`
- `crates/clap-tui/src/view/form.rs`
- `crates/clap-tui/src/view/command_tree.rs`
- `crates/clap-tui/src/view/argv.rs`

### Acceptance criteria

- `update` no longer imports rendering-oriented modules for business decisions
- `navigation` no longer imports `ui::dropdown`
- the same behavior remains covered by existing tests

## Phase 2: Split `AppState` into narrower mutation surfaces

Goal: keep the current state model but stop exposing it as one universal mutable bag.

### Work

- Keep `AppState` as the composition root.
- Add focused methods or helper types around:
  - command selection
  - form value mutation
  - focus and tab changes
  - dropdown lifecycle
  - notifications
- Replace direct field mutation in reducers where practical.
- Hide state internals behind crate-private methods once usage is migrated.

### Target files

- `crates/clap-tui/src/input.rs`
- `crates/clap-tui/src/update.rs`
- `crates/clap-tui/src/controller/navigation.rs`
- `crates/clap-tui/src/form_editor.rs`

### Acceptance criteria

- the hot interaction paths use explicit state methods instead of ad hoc field mutation
- transient UI invariants are concentrated in fewer places
- direct writes to `state.ui.*` are materially reduced

## Phase 3: Introduce a correctness pipeline

Goal: make argv preview and validation flow through one internal seam instead of
being recomputed ad hoc in multiple layers.

### Work

- Introduce a crate-local derived-state pipeline with explicit stages:
  - editable raw input state
  - effective command input state
  - argv plan / serialized argv
  - clap-backed validation result
- Keep reducers responsible for mutating raw state only.
- Move argv construction behind a single internal module that is shared by both
  preview and run paths.
- Introduce a validation model that can be consumed by UI code without forcing
  UI modules to understand clap parser rules directly.
- Ensure `view::argv` becomes a presentation layer over precomputed preview and
  validation data rather than a place where correctness rules are decided.

### Target files

- `crates/clap-tui/src/input.rs`
- `crates/clap-tui/src/argv_serializer.rs`
- `crates/clap-tui/src/view/argv.rs`
- `crates/clap-tui/src/app.rs`
- new derived-state / validation modules under `crates/clap-tui/src/`

### Acceptance criteria

- preview argv and run argv are produced by the same internal pipeline
- reducers do not directly decide argv omission or validation rules
- `view::*` modules no longer own correctness logic
- validation results are exposed through a small UI-facing model

## Phase 4: Break interaction handling into concern-specific modules

Goal: make interaction growth more additive across both reducers and event mapping.

### Work

- Replace the current large reducer with modules by concern:
  - `global`
  - `sidebar`
  - `form`
  - `dropdown`
  - `pointer`
- Narrow the responsibility of keyboard and mouse dispatch so new interaction
  behavior does not always require edits in one large controller file.
- Keep action-routing pressure out of a few central files where practical, even
  if a small top-level dispatcher remains.
- Keep a thin top-level dispatcher that routes actions.
- Move action-specific normalization into the relevant reducer where possible.
- Keep `Effect` as the boundary to runtime side effects.

### Target files

- `crates/clap-tui/src/update.rs`
- new files under `crates/clap-tui/src/update/`
- `crates/clap-tui/src/controller/keyboard.rs`
- `crates/clap-tui/src/controller/mouse.rs`

### Acceptance criteria

- adding a new dropdown behavior does not require modifying unrelated sidebar/form reducers
- adding a new interaction behavior is less likely to require edits in both a
  large controller file and a large reducer file
- reducer tests are grouped by concern
- top-level dispatch becomes substantially smaller

## Phase 5: Separate semantic argument traits from presentation traits

Goal: stop using widget-oriented categories for non-UI rules.

### Work

- Keep `ArgModel` as the clap projection boundary.
- Split current `InputPresentation` usage into two concepts:
  - semantic traits needed by serialization and validation
  - presentation traits needed by UI selection/rendering
- Update `argv_serializer` to depend on semantic properties instead of widget categories.

### Target files

- `crates/clap-tui/src/spec.rs`
- `crates/clap-tui/src/argv_serializer.rs`
- `crates/clap-tui/src/form_editor.rs`
- `crates/clap-tui/src/ui/form.rs`

### Acceptance criteria

- serialization no longer switches on widget presentation variants
- semantic rules can evolve without dragging UI code with them

## Phase 6: Move layout decisions behind an interaction-geometry boundary

Goal: stop letting navigation and reducers depend on UI layout helpers.

### Work

- Keep `FrameSnapshot` as the hit-testing contract.
- Introduce an explicit geometry builder phase that computes:
  - form viewport
  - input rects
  - dropdown rect and visible rows
  - tab hit targets
  - sidebar item hit targets
- Let reducers consume `FrameSnapshot` only, not `ui::*` layout helpers.
- Remove reducer/navigation imports of `ui::dropdown::dropdown_layout`.

### Target files

- `crates/clap-tui/src/frame_snapshot.rs`
- `crates/clap-tui/src/ui/screen.rs`
- `crates/clap-tui/src/ui/form.rs`
- `crates/clap-tui/src/controller/navigation.rs`

### Acceptance criteria

- interaction code depends on geometry data, not widget layout functions
- render becomes a projection over precomputed layout and view models

## Phase 7: Re-evaluate public seams after the internal cleanup lands

Goal: only after internal cleanup, decide whether public APIs should change.

### Work

- Review whether `Runtime` should be narrowed further.
- Review whether more crate-local types should remain private.
- Document supported extension points:
  - custom runtime
  - theming/configuration
  - command startup selection

### Target files

- `crates/clap-tui/src/runtime.rs`
- `crates/clap-tui/src/lib.rs`
- `README.md`

### Acceptance criteria

- any public API changes are justified by concrete internal simplification
- extension points are documented and intentional

## Suggested execution order

This refactor plan should not be executed in isolation. It should be sequenced
with `agent-docs/2026-03-15-2052-clap-feature-implementation-plan.md`.

Recommended combined order:

1. Refactor Phase 0
2. Refactor Phase 1
3. Refactor Phase 2
4. Refactor Phase 3
5. Feature Milestone 1
6. Feature Milestone 2
7. Feature Milestone 3
8. Refactor Phase 5
9. Refactor Phase 6
10. Feature Milestone 4
11. Feature Milestone 5
12. Refactor Phase 4
13. Feature Milestone 6
14. Feature Milestone 7
15. Refactor Phase 7

Reasoning:

- Phase 0 makes the rest of the work serve explicit library seams.
- Phases 1 and 2 remove the worst dependency and state-boundary problems before
  the richer clap model lands.
- Phase 3 establishes the authoritative correctness pipeline early enough that
  richer clap semantics do not get implemented separately in preview, reducer,
  and run paths.
- Feature Milestones 1 through 3 should happen after that pipeline exists but
  before the semantic/presentation split is finalized, because they redefine the
  actual domain model.
- Phase 5 should happen only after the richer spec and validation model exist.
- Phase 6 becomes simpler once both the richer model and the earlier query/state
  cleanup are in place.
- Phase 4 still matters, but it should happen after the new interaction surface
  is clearer so the reducer/controller split reflects real feature pressure.
- Phase 7 should remain late, but not because public seams were ignored earlier;
  it is a final re-check after the internal and feature work has settled.

## Risk and mitigation

### Highest risk

- form interaction regressions
- dropdown scrolling/selection regressions
- command tree selection regressions
- preview/run correctness drift while the clap model is expanded

### Mitigation

- add focused tests before each phase moves logic
- keep patches small and behavior-preserving
- run both unit tests and example smoke checks after each milestone
- add pipeline tests that assert effective state, argv output, and clap-backed
  validation together

## Concrete first slice

Start with Phases 0 through 3 in the smallest useful scope:

1. document the intended public extension points and constraints
2. extract `visible_args` and command-tree queries into a neutral internal module
3. replace `update` imports of `view::*` with that query module
4. replace `navigation` imports of `view::*` and `ui::dropdown` where feasible
5. introduce a minimal derived correctness snapshot shared by preview and run
6. route argv generation through that shared pipeline before feature-model expansion
7. keep all current tests green before moving to deeper state-boundary cleanup or richer clap semantics

This slice gives the best architectural leverage with limited behavior risk and
reduces the chance of later feature work building on the wrong seams or
duplicating correctness logic across layers.

## Validation checklist per phase

- `cargo test -p clap-tui`
- `cargo clippy -p clap-tui --all-targets`
- smoke-check:
  - `cargo run -p clap-tui --example simple`
  - `cargo run -p clap-tui --example subcommands`

# clap-tui review

Reviewed against SOLID principles, library-oriented Rust design, and general architectural quality.

## Findings

1. High: positional arguments with constrained values are serialized incorrectly.
   `crates/clap-tui/src/spec.rs:104-112` classifies any argument with `possible_values` as `ArgKind::Enum` before checking whether it is positional. `crates/clap-tui/src/view/argv.rs:46-50` then serializes every enum as `arg.name` plus the selected value. For a positional `value_enum` or any positional with `possible_values`, this emits an extra token and produces the wrong argv shape. This is a behavioral bug in the core model. The fix is to model "positional vs option" independently from "free text vs constrained values" and serialize based on position, not on whether the value set is enumerable.

2. High: terminal/session cleanup is not exception-safe.
   `crates/clap-tui/src/app.rs:86-116` manually enables raw mode, enters the alternate screen, and later tries to unwind those changes with ordinary `?`-based calls. If setup fails after raw mode is enabled, or if any cleanup step fails, the remaining cleanup steps are skipped and the caller can be left with a broken terminal session. For a library crate, that is too fragile. This should be wrapped in an RAII session/guard type with a `Drop` implementation that performs best-effort restoration regardless of where the error occurs.

3. Medium: the state model violates single responsibility and couples the view back into the core state.
   `crates/clap-tui/src/input.rs:97-117` stores command data, input values, `TextArea` widget state, layout rectangles, hover targets, mouse-selection state, scrolling, and toast timing in one struct. It also depends on the view layer directly through `visible_args` in `crates/clap-tui/src/input.rs:195-199`. The render path then mutates controller-consumed state in multiple places, for example `crates/clap-tui/src/ui/form.rs:26-30`, `crates/clap-tui/src/ui/form.rs:45-54`, `crates/clap-tui/src/ui/form.rs:121-124`, `crates/clap-tui/src/ui/form.rs:186-189`, `crates/clap-tui/src/ui/sidebar.rs:33`, `crates/clap-tui/src/ui/sidebar.rs:70`, and `crates/clap-tui/src/ui/sidebar.rs:78-128`. That creates bidirectional coupling between model, controller, and render code. A cleaner split would keep durable command/input state separate from ephemeral layout snapshots and widget-specific interaction state.

4. Medium: the library core is tightly bound to concrete infrastructure instead of abstractions.
   `crates/clap-tui/src/app.rs:86-123` hard-codes `Stdout`, `CrosstermBackend`, and the polling/event loop, while `crates/clap-tui/src/app.rs:173-178` hard-codes `arboard::Clipboard`. That makes the crate harder to test, harder to embed into another event loop, and harder to extend to alternate backends. From a DIP perspective, the library should depend on small traits for terminal session management, event input, and clipboard behavior, with default implementations for crossterm/arboard.

5. Medium: the public API is application-oriented instead of library-oriented.
   `crates/clap-tui/src/app.rs:57-59` and `crates/clap-tui/src/app.rs:72-75` require callback closures to return `anyhow::Result<()>`, and `crates/clap-tui/src/app.rs:68` / `crates/clap-tui/src/app.rs:83` convert callback failures into `TuiError::Terminal`. That forces downstream users into `anyhow`, erases typed domain errors, and misclassifies application callback failures as terminal failures. In a library API, prefer either `F: FnOnce(...) -> Result<(), E>` with `E: std::error::Error + Send + Sync + 'static`, or a distinct `TuiError::Runner(Box<dyn Error + ...>)` variant. Separately, `crates/clap-tui/src/app.rs:48-53` turns cancellation into `Ok(Vec::new())`, which is also an awkward sentinel in a public library API.

6. Medium-low: the render loop does avoidable cloning and allocation every frame.
   `crates/clap-tui/src/ui/screen.rs:31-47` clones the current `CommandSpec`, clones every visible `ArgSpec`, and clones `CommandInputs` into `ScreenView` on each draw. The loop in `crates/clap-tui/src/app.rs:131-168` redraws continuously, so this cost is paid throughout the session. It is acceptable for tiny CLIs, but it does not scale well and is unnecessary because most of that data is immutable for the duration of the app. Borrowed view models or a precomputed immutable command graph would reduce churn and simplify ownership.

## Open questions

- I assumed the crate intends to support arbitrary valid `clap` command graphs, not just a restricted subset. If a subset is intentional, it should be documented explicitly because the current spec conversion is lossy.
- I treated this primarily as a reusable library, not just an internal app. That raises the bar for terminal safety, typed errors, and infrastructure abstractions.

## Validation

- `cargo test`
- `cargo clippy --all-targets --all-features` (passes with warnings; findings above are based on source inspection, not just lint output)
